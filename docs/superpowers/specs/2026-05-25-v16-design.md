# v16 — UX polish, print dashboard improvements, cross-screen week selection

**Date:** 2026-05-25
**Forks from:** v15.3 (`55c838f`, local; or `cc761de` on `origin/v15`)
**Status:** Brainstormed + design-approved by user. Awaiting implementation plan.

## Why v16

Five focused improvements that emerged from v15 smoke testing and follow-up feature requests:

1. **Search/filter on long tables** — Issues + Outlier "Disertakan" lists get a name-only search box in the screen header.
2. **Minimum keyboard shortcuts** — Ctrl+F focuses search, Esc closes dialogs, Enter submits primary CTA.
3. **Branded About dialog** — long-deferred. New sidebar item "About" opens a JTS-branded modal showing version, build, Python, DB path.
4. **Print dashboard improvements** — dynamic header badge (WEEKLY/MONTHLY), period name in H1, KPI deltas vs previous period, resolution rate strip, outlier transparency line above page-2 ranking.
5. **Cross-screen week selection** — week picked on one screen (Issues, Dashboard, Coaching) follows the user to the others instead of resetting to "Semua".

All five are scoped tight; together they fit one milestone. None block any of the others — they can ship in any order during implementation.

## Feature 1 — Search/filter on Issues + Outlier

### Motivation

Issues table on a multi-week month easily has 50+ rows; finding one employee requires scrolling. Outlier's "Disertakan" list grows with the company roster. A live filter cuts time-to-find from "scroll until you see them" to "type three letters."

### Architecture

New reusable component `src/ui/components/search_bar.py`:

```python
class SearchBar(ctk.CTkFrame):
    """Pill input with placeholder, clear button, and 'N of M' counter.

    Emits on_change(query: str) on every keystroke. Caller is responsible
    for the actual filtering — this component is just the input UI.
    """

    def __init__(self, parent, on_change: Callable[[str], None],
                 placeholder: str = "🔍 Cari karyawan...", **kwargs):
        ...

    def set_count(self, visible: int, total: int) -> None:
        """Update the 'N dari M' counter display."""
        ...

    def get(self) -> str:
        """Current query text."""
        ...

    def clear(self) -> None:
        """Clear input + counter, emit on_change('')."""
        ...

    def focus(self) -> None:
        """Move keyboard focus into the input."""
        ...
```

Layout: `[🔍 input field] [✕ clear] [N dari M counter]` packed side="left" inside a transparent CTkFrame. Counter is `font=FONT_SMALL`, `text_color=COLOR_TEXT_DIM`.

### Wiring — Issues screen

One shared `SearchBar` in `_build_header()`, positioned between the screen title and the existing `+ Resolve Massal` button.

```python
self._search = SearchBar(header, on_change=self._apply_filter)
self._search.pack(side="left", padx=(SPACE_LG, SPACE_LG), fill="x", expand=True)
```

New method `_apply_filter(query: str)`:

- Iterates `self._row_cache` (the existing cached row data).
- For each row: keep iff `query.lower() in row["nama"].lower()`. Empty query → show all.
- Re-renders both Open and Resolved treeviews from the filtered list. The treeviews already get rebuilt on `_reload()`; this just calls the rebuild path with a filtered subset.
- Updates `self._search.set_count(visible_total, all_total)`.

Filter state lives on the screen instance (`self._search_query`) and survives period switches (clicking Minggu 1 → Minggu 2 with "Budi" in the box keeps "Budi" filtered). Navigating away and back resets the filter, because the screen is destroyed and recreated.

### Wiring — Outlier screen

Same `SearchBar` in the header. Filters the "Disertakan" section only (not "Dikecualikan" — that list is short by design, and excluding a hidden employee would be confusing). When the search box is empty, both sections render fully.

### Behavior — locked

- Live filter as user types (no debounce — Issues row count is <500, filtering is trivial)
- Case-insensitive substring match on employee name only (not department, not reason text)
- ✕ clear button always visible; counter shows `N dari M` (e.g., "3 dari 47")
- Filter persists across period switches on the same screen, resets on screen navigation

### Tests

- `tests/test_search_bar.py` (new): component construction, set/get/clear roundtrip, callback fires on input, counter updates via `set_count`.
- `tests/test_issues_screen.py` (extend): `_apply_filter("budi")` reduces visible row count; empty query restores all; counter updates.
- `tests/test_outlier_screen.py` (extend): same pattern for the Disertakan section.

## Feature 2 — Minimum keyboard shortcuts

### Motivation

Power-user polish. Three bindings, no central registry, no shortcut help dialog. The "Maximum" tier (Ctrl+1..9 to switch screens, F1 cheat-sheet) was explicitly deferred per brainstorming decision.

### Scope — locked

| Key | Where | Effect |
|---|---|---|
| **Ctrl+F** | Issues, Outlier screens (when `SearchBar` is present) | `self._search.focus()` |
| **Esc** | Every `CTkToplevel` dialog (Resolve, Resolve Massal, Holiday CRUD, Settings, About) | Call the dialog's close/cancel method |
| **Enter** | Same dialogs as above | Invoke the primary CTA button's command |

### Implementation notes

- Ctrl+F: bind on the screen frame via `self.bind("<Control-f>", lambda e: self._search.focus())`. No global binding — Outlier and Issues each bind locally so the shortcut is scoped to the visible screen.
- Esc: most CTk dialogs in this codebase already bind Escape (e.g., Batch Resolve at `batch_resolve_dialog.py:131`). The audit pass: ensure all 5 dialogs follow the same pattern. Where missing, add `self.bind("<Escape>", lambda e: self._on_cancel())`.
- Enter: bind on the dialog's main body frame via `self.bind("<Return>", lambda e: self._on_submit())` with `return "break"` to prevent default newline-in-entry behavior. The About dialog's only "submit" is Tutup; bind to that for consistency.

No tests for shortcut bindings beyond structural assertion that the bind is present (per the v15 lesson: headless tkinter can't reliably verify visual/focus side effects).

## Feature 4 — Print dashboard improvements

Four sub-changes to `src/reports/templates/dashboard.html.j2` and `src/reports/html_renderer.py`. Skipped: page numbering and `// ` h2 prefix cleanup (explicit user preference to keep developer aesthetic in section headers).

### 4a — Dynamic header badge

Currently hardcoded "WEEKLY REPORT" even on monthly prints. Replace with period-type-driven label:

| Period type | Badge text |
|---|---|
| Mingguan view | WEEKLY REPORT |
| Bulanan view | MONTHLY REPORT |
| Multi-month / custom | PERIOD REPORT |

Renderer signature additions: `render_dashboard_html(..., period_type: str = "monthly")`. Default keeps backward compatibility for any caller that hasn't been updated. Real caller is `dashboard.py`, which already knows whether the current tab is Mingguan or Bulanan; it passes `"weekly"` or `"monthly"` accordingly when invoking the renderer from the print dialog flow.

Template: replace `<div class="badge">WEEKLY REPORT</div>` with `<div class="badge">{{ period_badge_text }}</div>` (renderer computes the text from `period_type`).

### 4b — Period in H1

Current: `<h1>HR Absensi Dashboard</h1>` with period only on the right meta block.

New: `<h1>HR Absensi Dashboard <span class="sep">·</span> <span class="period">{{ period_label }}</span></h1>` where `.sep` is muted gray and `.period` is cyan (matching the existing right-meta accent). Right meta drops the duplicated `period_label` line; keeps only `period_start — period_end` and `Gen: ...`.

### 4c — KPI deltas vs previous period

Each of the 4 KPI cards gains a delta line below the existing "kejadian"/"min"/etc subtext. Format: `▼ N dari minggu lalu` (or `bulan lalu` for monthly view), colored green for improvement, pink/rose for worsening, gray for no change.

**Direction-of-good per metric:**

| KPI | Better when |
|---|---|
| Total Terlambat | ↓ (lower) |
| Rata-rata / Kejadian | ↓ |
| Coaching | ↓ |
| Teladan | ↑ (higher) |

Computation: in `html_renderer.py`, before rendering, compute the previous-period range (previous week or previous month based on `period_type`), call the same insight functions with the previous range, compare. Pass a `kpi_deltas` dict to the template:

```python
kpi_deltas = {
    "total_terlambat": {"delta": -8, "direction_good": "down"},
    "avg_min":         {"delta": +2, "direction_good": "down"},
    "coaching":        {"delta": -1, "direction_good": "down"},
    "teladan":         {"delta": +2, "direction_good": "up"},
}
```

Template uses `delta` sign + `direction_good` to pick arrow (▼/▲) and color class. When no previous period exists (first period in DB, or month before earliest data), pass `delta = None` → template renders an em-dash and no color.

### 4d — Resolution rate strip

New inline element between the KPI grid and the Top 5 section:

```html
<div class="b-resolution">
  <strong>Status Issues:</strong> {{ open_count }} open · {{ resolved_count }} resolved
  <span class="pct">{{ resolution_pct }}% resolved</span>
  {% if resolution_delta is not none %}
    <span class="delta">{{ resolution_delta_arrow }} {{ resolution_delta_pct }}% dari bulan lalu</span>
  {% endif %}
</div>
```

Computed in `html_renderer.py` via existing `resolution_rate(conn, period_start, period_end)` in `src/core/insights.py` (already implemented; just not surfaced in print). Previous-period delta uses the same previous-range trick as 4c.

Styled with light pink/rose background tint to match the magenta accent without competing with the KPI cards.

### 4e — Outlier transparency line above page-2 ranking

Above the ranking table on page 2:

```html
{% if outlier_count > 0 %}
<div class="outlier-note">
  {{ outlier_count }} karyawan dikecualikan dari analisa: {{ outlier_names }}
</div>
{% endif %}
```

Computed in `html_renderer.py` via `src/db/outlier.py::list_active_exclusions(conn, period_start)`. Pass `outlier_count` (int) and `outlier_names` (comma-joined string) to the template. When count is 0, the entire div is omitted.

## Feature 5 — Cross-screen week selection

### Motivation

User pain point: pick "Minggu 1" on Issues, switch to Coaching to see who needs coaching that week — Coaching defaults back to "Minggu 1" (its hardcoded default) or "Semua" (for the others). Have to re-pick the week on every screen.

### Architecture

New file `src/core/session_state.py`:

```python
"""Session-only UI state shared across screens — does NOT persist to DB.

Currently holds the focused-week key. Could be extended with other
ephemeral cross-screen state in future versions (e.g., last-searched query).
"""


class SessionPeriodState:
    """Holds the user's currently-focused week key.

    Default 'semua' on app launch. Updated only by explicit user clicks
    in any screen's WeekNavBar — internal WeekNavBar fallbacks (when
    'semua' is requested on a screen with include_all=False) do NOT
    write to this state.
    """

    def __init__(self):
        self._week_key = "semua"

    def get(self) -> str:
        """Returns 'semua' or 'minggu_N' (N in 1..6 per month length)."""
        return self._week_key

    def set(self, key: str) -> None:
        if not key:
            return  # defensive: empty key ignored
        self._week_key = key

    def reset(self) -> None:
        """For test isolation. Production code should never call this."""
        self._week_key = "semua"


# Module-level singleton. One instance per app process.
period_state = SessionPeriodState()
```

### Wiring — 3 touch points (Issues, Dashboard, Coaching)

Each screen, in the `WeekNavBar` construction:

```python
from src.core.session_state import period_state

# In _build_header() or wherever WeekNavBar is constructed:
self.nav = WeekNavBar(
    header,
    current_month=self._current_month,
    on_change=self._on_period_change,
    initial=period_state.get(),       # ← read shared state
    include_all=...,                  # unchanged per screen
)

def _on_period_change(self, key):
    period_state.set(key)              # ← write shared state
    self._reload()
```

That's it. 2 lines added per screen (import + one parameter change + one method-body line). The existing `WeekNavBar` fallback logic (lines 50–51 of `week_nav.py`) handles the "semua → Coaching" case automatically: `if self._active not in self._buttons and self._buttons: self._active = next(iter(self._buttons.keys()))`. The fallback is internal display only — it does not call `on_change`, so it does not update `period_state`.

### Cross-screen behavior matrix

| Scenario | Result |
|---|---|
| Launch app, Issues at "Semua" | Dashboard + Coaching see `period_state.get() == "semua"` on first visit |
| Issues clicks Minggu 2 → Dashboard | Dashboard shows Minggu 2 |
| Issues at Minggu 2 → Coaching (`include_all=False`) | Coaching shows Minggu 2 |
| Issues at "Semua" → Coaching | Coaching's WeekNavBar internal fallback selects Minggu 1; shared state stays "semua"; back-to-Issues shows "Semua" |
| Coaching clicks Minggu 3 → back to Issues | Issues shows Minggu 3 |
| Switch active month May → June | New WeekNavBar built with June weeks. Existing fallback handles invalid keys (e.g., "minggu_5" not in June). Shared state stays the picked key unless user clicks something explicitly. |

**Key invariant:** internal `WeekNavBar` fallback does NOT write to `period_state`. Only explicit user clicks (which go through `on_change` → `_on_period_change` → `period_state.set`) update shared state.

### Tests

- `tests/test_session_state.py` (new): defaults to "semua"; `set` updates; `get` returns latest; `reset` returns to "semua"; empty string passed to `set` is ignored.
- `tests/test_issues_screen.py` (extend): instantiate, simulate pill click via `dlg.nav._on_click("minggu_2")`, verify `period_state.get() == "minggu_2"`. Then construct `DashboardScreen` in the same test, verify its `nav.active == "minggu_2"`.
- All 3 screen-construction tests get a `conftest.py` fixture `reset_period_state` (autouse, function-scoped) that calls `period_state.reset()` to prevent state bleeding between tests.

### Scope guards

- No DB persistence (user's choice: session-only).
- No reactive notification — screens rebuild on navigation, so read-on-mount is sufficient.
- No new screens get week nav added — only the 3 that already use `WeekNavBar`.
